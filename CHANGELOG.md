# Changelog

## Unreleased

- Linear landing: landed PRs now end merged. One `updateRefs` moving `main` and the PR branches left every PR closed and not merged on real GitHub. The branches now move first and `main` second, in two calls, each compare-and-swapping what the other relies on. A branch can read at its stack commit with `main` unmoved between the calls; if the landing does not complete, qlander moves it back itself, with a write that cannot unwind a landing or overwrite a push. The queue no longer leaves that to an operator. Each landed PR now gets `pull_request` runs on its stack commit, which nothing reads.
- Linear landing: a landed PR that ends closed and not merged now gets a comment and loses `ready`, after a wait for a late mark, instead of being dropped silently. Merge mode is unchanged.
- Linear landing: a PR carrying commits that landed squashed is refused at build with a comment until it is rebased, since a merge would silently drop anything it undoes of them. A PR stacked on another in the same batch is unaffected. Records the commits in a new `squashed` state field, kept if the repo switches to merge mode. A state with a stack from an unreleased build refuses and pauses. Merge mode on a repo that never landed linear reads and writes nothing new.
- Linear landing: seen-red entries (`queue.strategy.skipSeenRed`) are no longer carried across a landing, since a PR stacked on one that landed could merge to a different tree.
- Linear landing: a PR title that could read as a trailer or as qlander's own line gets the subject `Pull request #<number>` and a `Title:` line, as merge commits do.
- Linear landing: a branch protected only by rulesets is no longer reported as having classic protection. GitHub's `protected` flag is true for both, so such a branch came out `unknown` at admission, and `audit` T13 asked for an admin token to read protection it didn't have. Both now read `protection.enabled`.
- Linear landing: admission and `audit` T13 now count every rule that refuses the landing's forced update of a PR branch, from one list: `non_fast_forward`, `update`, `pull_request`, `required_status_checks`, `required_deployments`, `merge_queue`, `workflows` and `code_scanning`, plus `required_signatures` with `queue.landing.author: author`. Before, a `required_status_checks` rule on a PR branch passed T13 and refused the landing. A PR on such a branch now waits at admission with a comment until the queue App may bypass the rule (mode `always`). Rules that depend on the commit's content, such as message patterns and file restrictions, are not judged in advance.
- `render` now keeps the qlander download in `ci.yml` and `verify-sandbox.yml` in line with `bundle`, so changing `bundle.repo` or `bundle.private` no longer breaks control CI until they are edited by hand. Those files stay hand-editable and `render` changes nothing else in them. Existing control repos don't break: with the default repo the download already matches, so `render --check` and audit C7 report nothing new except a C7 `PASS` line for each file. If the download differs, `render --check` prints a note and still exits 0, and C7 is a `WARN`; run `render` to update it. A file with no recognisable download, a missing file and source mode are left alone. Your existing files keep their old header comment, which is harmless.
- `setup --apply`: when GitHub refuses a ruleset that adds a `release.dispatch.promoterApps` entry, the failure now names the ids and what to check, instead of only `validation (422): Validation Failed`.
- `audit` T10 now fails when `release.dispatch.promoterApps` lists the queue or state App, or the release-landing ruleset gives one of them bypass, as `setup` already refuses. It also fails when `release.dispatch.workflow` does not exist on `release.dispatch.ref`; with `release.dryRun` that is a `WARN`, like T10's other gaps.
- Release dispatch mode: a run that reports success but whose jobs never say when it completed now ends as `unverified` after `release.dispatch.runHours`, instead of holding the candidate forever. It never counts as a pass: a dry run ends the candidate, and a real run pauses the release job as any run that could not be followed.
- Release dispatch mode: turning `runner.epochFence` off no longer leaves the release job `busy` forever. The token stays Contents: read, and only when voiding the recorded epoch branch is refused does the job mint a Contents: write token and run the tick once more. This adds two guarded steps to `tick.yml` with `release.mode: dispatch` and the fence off, so re-render there. Other configurations render as before.
- State and the policy hash are unchanged.

- Merge mode: a merge commit's subject is now `<PR title> (#<number>)`, so `git log` shows what landed. The body keeps the head (`Merged from #<number> at <head>.`) and `Landed-by: qlander batch <n>`, and drops the `Title:` line, which the subject replaces. A PR with no title keeps `Merge pull request #<number> at <head>`, and so does a title that could read as that subject, a trailer or a patch divider, with its title on a `Title:` line as before. If you parse merge subjects, also accept the ` (#<number>)` ending: old history keeps the old form. State and the policy hash are unchanged.
- Linear landing, opt in with `queue.landing.mode: linear`, for repos that require linear history and squash-style commits. Each batch is built as a stack of single-parent commits on main, one per PR, on the same tree merge mode tests, and lands in one compare-and-swap update that also moves each PR's head branch to its stack commit, so GitHub marks the PR merged. An author push since admission refuses the whole update; that PR is dropped and the rest rebuild. `queue.landing.author` picks the commit author, admission and audit T13 check that the head branches can be force-updated, and a refused landing is retried before it pauses (`queue.landing.maxRefusals`). Linear mode can't be combined with release advance mode. Merge mode is unchanged, and so are its state and policy hash.
- Release dispatch mode (`release.mode: dispatch`, opt-in). The release job never writes `release`: for the newest qualified `main` commit it dispatches the target's own release workflow as a dry run, reports a green one on the status issue, waits for `/qlander approve-release <sha>` from one of `release.dispatch.approvers`, then dispatches the real run, and counts release as advanced only when it sees the ref there. Each sha gets at most one dry run and one real run. Dispatches are journalled, never resent, budgeted, fenced, paused by `release-pause` and stopped by optional freeze variables. A dispatched run counts only if GitHub reports the release App's bot (`release.dispatch.actor`) as its actor and triggering actor, and the dry run is checked again right before the real one. In this mode the release App gets least privilege: Actions: write, Contents: read (write only with the epoch fence), no Workflows, Variables: read with a freeze, and no bypass on the release ruleset; change its permissions before you switch. A real run that does not end green with `release` seen at the commit pauses the release job (not the queue). An approver can re-arm a sha for one more attempt (`/qlander rearm-release <sha> <incident>` or `rearm-release <sha>`), from a fresh dry run and a fresh approval. Only `release.dispatch.promoterApps` and named users may bypass the release ruleset. New commands: `approve-release <sha>`, `rearm-release <sha>`. `audit` T12 checks that what the promote workflow runs is inside `queue.policy.paths`. Switching back to advance mode while a real run is still open pauses the release job. Linear landing is allowed with dispatch mode, but a hotfix on `release` then can't be merged back, so fix forward on `main`. Advance mode, its state and the policy hash are unchanged; a dispatch-mode state has an extra `dispatch` field, which older releases refuse.
- Linear landing with release dispatch mode: `release` now only ever fast-forwards to `main` commits. `setup` adds "restrict updates" to the release-landing ruleset, so only its bypass actors (`release.dispatch.promoterApps` and the break-glass people) can move `release` and no hotfix PR can be merged into it; fix forward on `main` instead. `audit` T10 fails without that rule, or when a promote App is not an `always` bypass actor on every ruleset that would stop it moving `release`, and no longer checks that pre-landing workflows run on PRs into `release`. Validation refuses `queue.landing.author: author` with dispatch mode, since its unsigned commits could never be promoted. Merge mode is unchanged. Setup only tightens, so after switching back to merge mode remove the rule by hand to reopen the hotfix path.

## 0.2.3

One fix and a documentation update. State is unchanged, so this release reads what 0.2.2 wrote, and the policy hash is unchanged, so no admitted PR loses its place.

- A batch no longer waits forever when GitHub reports its CI run `completed` but still lists one of its jobs as `in_progress` (or `queued`), even with that job's conclusion and `completed_at` set. Before, the in-progress timeout skipped completed runs, so the batch stayed pending until someone bounced the PR. Such a job still never counts as a pass. Once it is past `queue.timeouts.inProgressMinutes` from its own start, or the attempt is past the usual caps, the queue pauses with a configuration problem that names the run and the job, and the batch's PRs go back to the front of the queue with `ready` kept (or are parked, with `queue.strategy.reuseGreen`). Close the pause to carry on. A failure conclusion on such a job is still red at once.
- Docs: new runbooks for renaming the control repo, an App or a label, and for a job still running after its run finished; when ticks run, and why a new repo can go hours without a scheduled run; full command forms in both agent guides; the check before merging a config change accepts a queue state that is still `absent` before the first live tick; and a wording pass over the install and operating guides and the template.

## 0.2.2

Fixes from the first full end-to-end run of the queue, in a scratch organisation. State is unchanged, so this release reads what 0.2.1 and 0.1.0 wrote, and the policy hash is unchanged, so no admitted PR loses its place.

- `quiesce` works on a queue no live tick has run. A missing queue state branch has nothing in flight, so it quiesces cleanly, unless the queue's state issue is open or can't be listed, or the branch was there when the command started. Those still refuse.
- `unquiesce` works in dry-run mode. A dry-run tick's report now says whether it found a pause or would raise one, and `unquiesce` checks that. A live tick must still report success, and `unquiesce` now also refuses if that tick reopened a pause, left one pending in its state, or the check can't tell.
- `unquiesce` closes only the pauses `quiesce` opened. A pause from `pause` or by hand makes it refuse unless you close that pause or pass `--all`, and `quiesce` and `pause` each open their own issue beside the other's.
- `quiesce` refuses before it changes anything for whatever would stop it later, including a landed PR being verified and an undelivered notice, so a queue isn't stopped when it can't finish. The check after the wait is unchanged.
- Refusals from `quiesce` and `unquiesce` name the way out, going by what is true then: `resume both` or `unquiesce` only when every open pause is that run's own. A pause that was already there is named and left alone, and the message gives the issues to close instead. A waiting `cancelRuns` entry shows when it can clear.
- `quiesce --dry-run` also reads the tick runs, and exits 1 when it prints `not idle now`, as it does for a tick still running.
- `audit` no longer asks for a restrict-updates rule on the release landing ruleset, which `setup` leaves out so that a person can merge a hotfix PR. If you added that rule to quiet `audit`, remove it, because it blocks that merge. `audit` now requires every check `setup` puts on that ruleset, so a release ruleset missing one of the full suite's jobs fails where it used to pass.
- Every download in a workflow retries a failed attempt within a hard limit, 40 seconds for Bun and 20 for the bundle, and is still checked against its sha256. A stalled download fails the job, which leaves the tick's work inside the 5-minute job limit. The runner needs `curl` 7.71 or newer and `timeout`. Run `render` when you take this pin: until you do, `render --check` and `audit` C7 report the difference. The old workflows still run this release.
- A `ready` PR whose fast lane is red gets one comment per head after 30 minutes, instead of waiting silently.
- The landing rules now say that a push drops a PR only after admission. Before that, a push changes what would land and `ready` stays on, so don't add `ready` until the head is final.
- Wording: the "ticks stopped" and "runner stuck" alerts no longer assume your own CI hosts, the status issue names `release.dryRun`, the mirror issues say when they are read, and an admission's evidence no longer carries deployment-specific text. The docs now say when T0 and C0 print, and that control commands comment on the status issue.

## 0.2.1

Fixes for a first run of `setup` against real GitHub.

- `setup --step verify` no longer fails on a ruleset that works. It judged a refused state branch by GitHub's wording, and a real refusal can read `Reference update failed`. It now needs a 422, the branch still absent, and GitHub reporting that ruleset's creation rule on that branch name. A failed read of those rules fails the check.
- `setup --skip-audit` no longer reports a clean audit when none ran, or names a command that bundle users don't have.
- If a key is already saved for an App when its manifest code arrives, `setup` keeps that key and checks it, instead of failing.
- For when GitHub's new-App form comes up empty, `setup` also prints a pre-filled link for each App. A waiting `setup` notices the App and its key and carries on.
- The steps for a new private key use GitHub's current labels: **Credentials**, then **Key pairs**, then **New key**.
